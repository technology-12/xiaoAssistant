# 正式版工作包与设计差异审查

日期：2026-11-01  
基线：PRODUCTION_IMPLEMENTATION_PLAN.md，重点为第 14 节 W01～W09 及相关验收条款。  
范围：当前 src、项目引用、tests 源码、README、PRODUCTION_PROGRESS.md 和已有验证记录。  
方式：静态源码审查；本轮没有改动应用代码、配置、二进制或 release，没有构建、运行测试、接入模型或操作用户文件。仅新增本审查报告。

## 一、结论

**当前不能确认九个工作包全部实现，更不能确认已达到正式版验收。**

- W02、W05、W06、W07 新增了较多功能代码，但均存在设计覆盖不全或实现缺陷。
- W04 只有 JSON/JSONL 及回执、会话存储基础，未完成计划中的 SQLite、事务化迁移、备份和故障恢复。
- W03 独立任务宿主/IPC、W08 安装签名更新未实现。
- W01 缺真实 Win7、真实模型/证书矩阵验收；W09 有测试基础，未完成正式版系统与试点验收。
- 按原方案的完整退出条件衡量，当前没有可确认“完整验收通过”的工作包；这不等于现有功能代码没有价值。

建议把当前阶段描述为“正式版功能增量/预发布原型”，不要把工程版本号 1.0.0 或页面文案当作正式版完成证据。

## 三、需要优先处理的具体实现问题

严重度：P1 为正式版前应优先修正的正确性/权限/数据风险，P2 为明确功能或可靠性缺口。下面均给出静态代码可推导的触发条件；未声称已在真实用户环境复现。

### F01 [P1] 切换 Profile 时，把旧表单写进新 Profile

- 位置：src/WorkAssistant.Desktop/SettingsWindow.xaml.cs:90，关键调用在 93～94 行。
- SelectionChanged 触发后，SelectedProfile 已经是新选项；代码先 WriteFormTo(SelectedProfile)，再 LoadProfileFields(SelectedProfile)。
- 触发：配置 A 与 B 有不同地址/模型/Key，当前表单显示 A，选择 B。
- 结果：A 的字段和 Key 被写入 B 的编辑副本；B 的原配置被覆盖，保存后可持久化。并不是注释声称的“先保存旧配置，再加载新配置”。
- 差异：W05 要求配置与凭据独立。当前存储层的多 Profile 测试不能覆盖该 UI 事件顺序错误。
- 验收补充：切换 A→B→A 保持各自字段；测试未保存草稿、取消与凭据不串写。

### F02 [P1] 输出文件已存在时跳过内容一致性校验

- 位置：src/WorkAssistant.Tools/TableReading.cs:56～64；TryReadArtifacts 在 143 行。
- CommitFiles 在“所有目标均存在”时直接读取当前文件摘要并返回，未比较现有字节与本次 Content；后面的 Commit 内容冲突检查被绕过。
- 触发：同任务再次生成同名 XLSX/DOCX，但输入结果或模板字段已经变化；或现有文件被改动。
- 结果：旧内容被当作本次新结果成功交付。哈希是对旧文件计算的，因此不会发现语义错误。
- 差异：W04/W06 要求幂等和校验，不能把“文件存在”当“正确内容已提交”。
- 验收补充：同内容复用；不同内容明确冲突或新版本；损坏文件不得注册成功。

### F03 [P1] 生成整理计划就可能把“执行整理”判为完成

- 位置：src/WorkAssistant.Tools/FilePlanTools.cs:53；src/WorkAssistant.Core/AgentController.cs:268、328。
- plan_file_organization 声明 ProducesArtifacts=true；Controller 只要某个此类工具成功就设置 producerSucceeded。
- 触发：用户要求实际整理，模型仅生成 organize_plan.md 后结束，未调用 apply_file_plan。
- 结果：任务可以 Completed，虽然原文件完全未移动。
- 差异：W02/§5.5 要求修改任务有“审批＋实际变更＋目标校验”证据。计划成果不能替代执行证据。
- 验收补充：只生成计划应处于待确认/计划完成的明确状态；不能计入用户要求的实际整理成功率。

### F04 [P1] 数据分析和截断响应仍可被当作完整成功

- 位置：src/WorkAssistant.Core/AgentController.cs:154、357～378；src/WorkAssistant.Infrastructure/HttpModelClient.cs:307、460。
- DataAnalysis 最终与问答共用“非空文本即成功”；未检查是否完成了实际计算，也不要求结果与来源证据。
- Controller 没有阻止 finish_reason=length/content_filter 等非完整结束的文本进入 Completed；流解析只检查是否存在结束标记/finish_reason。
- 触发：模型直接编造统计结果，或因输出长度限制只返回半段结论。
- 结果：界面可显示任务完成；与方案对“计算证据”和“完整响应”的要求不符。
- 验收补充：分析必须关联实际计算结果；区分正常结束、截断、过滤和断流。任务类型不能只依赖中文关键词猜测。

### F05 [P1] PDF 导出工具的元数据与完成判断不一致

- 位置：src/WorkAssistant.Tools/ExportXlsxTool.cs:302～309、375；src/WorkAssistant.Core/AgentController.cs:357。
- extract_pdf_text 可在 write_file=true 时登记 Markdown 成果，但 Definition 没有 ProducesArtifacts=true；Controller 的 producerSucceeded 不会因此成立。
- 触发：用户要求“提取 PDF 并生成报告”，推断为 FileGeneration，模型只使用该工具写出文本后结束。
- 结果：即使文件实际生成并登记，也可能被标为 NO_ARTIFACTS。
- 差异：W02 完成证据不能仅依赖一个与参数无关且配置不完整的布尔字段。
- 验收补充：同一工具只读/导出两种模式分别定义证据与结果类型。

### F06 [P1] 文件部分移动后取消或落盘失败，无法可靠识别与恢复

- 位置：src/WorkAssistant.Tools/FilePlanTools.cs:260～293；src/WorkAssistant.Core/AgentController.cs:385；计划存储在 FilePlanTools.cs:15。
- 每项移动前检查取消，但逐项变更只存在内存；file_mutations.md 等全部结束后才写。
- 在已移动一部分后取消：OperationCanceledException 越过移动异常处理，Controller 直接标记 Cancelled，未持久化已执行项和未执行项。
- 在全部移动后写变更清单失败：有副作用但未有完整日志；之前“计划产出成功”的标志还可能使任务最终显示成功。
- 崩溃重启时计划、AppliedSources 丢失；启动只标 Interrupted，不重建文件状态。
- 差异：W04/W06 要求阶段提交、每步记录与 NeedsReview；当前只覆盖了部分 IOException 路径。
- 验收补充：第 N 次移动后取消/断电、目录创建失败、日志磁盘满、回执写失败均留下可审计状态，不自动重复移动。

### F07 [P1] 演示模式可在真实授权目录自动批准移动文件

- 位置：src/WorkAssistant.Desktop/MainViewModel.cs:805～809；src/WorkAssistant.Core/FakeModelClient.cs:223～252。
- 演示模式仍使用实际工作区和实际移动工具，ApprovalProvider 直接返回 true；Fake 整理脚本会把发现的文件移到 inputs/已归档。
- 触发：普通界面选择真实业务目录，在默认演示模式输入“整理”或选择整理快捷任务。
- 结果：没有逐项用户确认就会移动原文件。界面“不联网”的提示不能等同于批准所有本地修改。
- 差异：§5.3/§9 要求具体变更先审批，自动批准只能限定在隔离的测试样例工作区。
- 验收补充：演示沙盒和真实授权目录分开；真实目录的写操作不因 Fake 模型而绕过审批。

### F08 [P1] Office/PDF 解压与解析缺少足够的资源上限

- 位置：src/WorkAssistant.Tools/PackageZip.cs:46；DocxWriting.cs:79；XlsxReading.cs:201；PdfText.cs:238。
- 对压缩包 entry 和 PDF Flate 流使用无界 CopyTo/MemoryStream；XLSX 先整体 XDocument.Load 再限制行数。
- 现有 10 MiB 等限制针对压缩文件，不能限制解压后内存、XML 规模、字段、列号或 PDF 对象数量。DOCX 模板复制还会遍历所有部件。
- 触发：小体积、高压缩比或异常结构文件。
- 结果：内存/CPU 可先被耗尽；由于 W03 未实现，UI 与任务在同一进程，取消未必能终止同步解析。
- 差异：§8.2、W03/W06/W09 的恶意文档、资源限制和取消要求尚未落实。
- 验收补充：解压累计字节/条目/压缩比、XML 长度/深度、最大列/字段、解析时间和 Worker 内存必须在读取过程中执行限制。

### F09 [P2] SSE 解析存在，但 HTTP 调用先缓冲整个响应

- 位置：src/WorkAssistant.Infrastructure/HttpModelClient.cs:163、190～192。
- 使用 HttpClient.PostAsync 默认完成行为，响应内容先缓冲完成后才进入 ReadAsStreamAsync/ParseSseStreamAsync。
- 结果：解析时确实会产生 delta 回调，但用户通常无法在服务器持续输出时实时看到；长响应先消耗缓冲内存，可能耗尽单次超时。
- 差异：W05 的真实流式体验尚未实现到网络层。
- 现有测试缺口：StreamingTests.cs:57～59 一次写完整 body 并关闭，只验证回调次数，没有验证“服务器结束前已收到首字”。
- 验收补充：分时分块发送并保持连接的测试，校验首片到达时间、取消和空闲/总超时。

### F10 [P2] 工具能力检测和连接成功状态可能虚报

- 位置：src/WorkAssistant.Infrastructure/HttpModelClient.cs:569～572；src/WorkAssistant.Desktop/MainViewModel.cs:241～273；App.xaml.cs:19～20。
- 测试请求要求“只回复 ok”，只因接口接受 tools 字段就把 ToolCallingOk 设为 true，没有收到和验证实际 tool_call。
- 连接状态是 App 全局布尔和文字，不绑定 Profile/端点/Key/代理指纹；更换配置后仍可能显示旧的连接成功。
- 差异：§5.1/§7.1 明确要求能力逐项验证，以及配置变更使旧状态失效。
- 验收补充：忽略 tools 的网关必须判能力未验证；配置 A 成功不应传递到 B。

### F11 [P1] XLSX “首工作表”定位可能读错表

- 位置：src/WorkAssistant.Tools/XlsxReading.cs:68～70。
- 只要 xl/worksheets/sheet1.xml 存在就直接返回，不先解析 workbook 的显示顺序和关系。
- 触发：工作簿将 sheet2 调整到第一张，sheet1 仍存在；Excel/WPS 正常支持这种操作。
- 结果：用户看到的第一张表与程序计算的表不同，可能静默汇总错误数据。
- 补充差异：日期保持序列值，公式无缓存时返回空字符串（267 行），未形成针对缺缓存的清晰提示。
- 设计范围：正式方案 §8.2 包含日期、缓存与必要时提示；不能在进度表中自行把全部日期语义移到 1.1 就视为满足原计划。

### F12 [P2] PDF 页码与多字体映射不能保证来源准确

- 位置：src/WorkAssistant.Tools/PdfText.cs:85～101、135。
- 页码按对象在文件中的出现顺序生成，没有按 PDF 页树顺序解析；ToUnicode 全文档合并，同编码在不同字体下会互相覆盖。
- 触发：页对象物理顺序与页树不同，或同页/跨页使用多种字体编码。
- 结果：可能得到看似成功但页号错误/字符错误的文本；不一定像进度说明所说统一报 UNSUPPORTED_FORMAT。
- 另外，107～111 行仍保留 TEMP-DIAG，向 stderr 写出解码流开头，可能将用户文档片段带入诊断输出。
- 验收补充：真实多字体/重排页/对象流文件，必须正确解析或明确拒绝，不能给错误页号引用。

### F13 [P2] 连续对话有摘要，但缺可追溯的输入与计算口径

- 位置：src/WorkAssistant.Desktop/MainViewModel.cs:489、492～493、573～590。
- 上轮只注入用户请求和助手前 600 字＋成果路径；工具参数、筛选/映射、输入版本和来源摘要不作为结构化事实保存并重用。
- 每轮新建聚合与计划暂存；文件继续从当前 inputs 读取，没有输入快照。
- 触发：“按刚才同样口径重算”时，上轮关键参数不在 600 字中，或源文件已变化。
- 结果：模型只能猜测原口径，结果可变而用户不知。存在对话能力，不代表 §7.3 的可追溯上下文已完成。

### F14 [P1] 存储层没有原方案要求的崩溃一致性

- 位置：src/WorkAssistant.Infrastructure/LocalTaskStore.cs:42～50、224～231、341～355；src/WorkAssistant.Core/ToolDispatcher.cs:82～85。
- task/session 保存先删旧文件再移动；回执直接覆盖写入。工具副作用完成后才 Put 回执，文件系统与回执之间没有 prepare/commit 意图记录。
- 触发：删旧文件后断电、回执写到一半退出、文件已移动但回执未登记。
- 结果：历史/会话/回执可丢失或损坏，无法确认操作是否执行，不具备正式版的可恢复性。
- MarkInterruptedTasks 只是状态标记，不是恢复；JSONL 也不能代替存储事务。
- 不应只用“换 SQLite”描述修复：还要完成文件提交协调、版本化 schema、备份与恢复测试。

## 五、现有测试为何不足以关闭这些差异

1. Profile 存储测试不等于 ComboBox 切换事件测试，无法发现 F01。
2. SSE 回调次数测试不等于实时首片延迟测试，无法发现 F09。
3. 整理冲突测试覆盖“执行前目标已存在”，不覆盖“移动一半后取消/崩溃/日志写失败”。
4. 文档 roundtrip 使用自身写出器构造样例，不能证明兼容 Excel/WPS 的全部正常工作簿结构或真实 PDF。
5. 任务分类测试覆盖了问答和文件无产出，但未证明“分析必须计算、计划不算实际修改、PDF 导出正确计入、截断不算完成”。
6. Headless UI 自检能验证状态与产物，不替代鼠标/键盘、配置切换、真实 DPI、屏幕阅读器或 Win7 验收。
7. 注册 61 个测试和历史 42 条 PASS 是工程基础，不能替代计划中的至少 50 个业务任务、故障注入和两周试点。

## 六、建议推进顺序（仅方案，不在本轮实施）
