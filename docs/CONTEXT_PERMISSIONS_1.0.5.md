# 晓助手 1.0.5：上下文整理与三档任务权限

## 上下文整理已经存在

1.0.4 已有自动上下文管理，1.0.5 增加可见状态：主窗口底部显示“上下文自动整理”“正在整理上下文…”及实际摘要整理次数。新对话重新计数，多轮对话使用最近的上下文投影继续。

实现包括：

- 历史达到192 KiB序列化字符的本机软阈值，或估算达到扣除输出预留后的模型窗口85%时，尝试整理。
- 先收起较早且较大的工具结果，以任务ID和调用ID回查引用代替；完整工具结果仍在本地步骤记录。
- 按完整的助手/工具回执组生成历史摘要，保留最近三个完整组和当前用户原始请求；摘要要求保留目标、已完成/未完成事项、文件引用、草稿与章节版本、阅读范围及用户决定。
- 下一轮使用最近成功任务的 ContextMessages，而不是再次注入全部旧历史。
- 摘要截断时缩小整理范围，在原有任务预算内受控重试；摘要被视为参考数据，不能扩大权限或代替精确计算证据。

原始会话没有被摘要覆盖或删除，需要精确内容时可通过 read_task_history 回查。窗口未知时仍有本机阈值；建议为自定义IP端点配置真实模型窗口。小历史、预算耗尽或摘要失败时有明确限制，不是无限压缩。这种机制减少历史内容占用，不能保证模型永不遗漏信息。

## 三个权限档位

右上角增加权限菜单，与模型选择相邻；默认“帮我批准”。点击选项自动保存，对新提交任务生效。

| 档位 | 自动执行 | 需要确认 |
|---|---|---|
| 帮我批准 | 阅读、计算、内部草稿、生成成果副本 | 修改、移动原文件和回滚等既有敏感工具 |
| 请求批准 | 阅读、计算、内部草稿保存和状态查询 | 最终生成成果文件、生成可交付修改提案、修改或移动原文件等操作 |
| 完全访问权限 | 自动批准当前授权工作区内已开放工具的文件操作 | 项目或角色明确配置为 ask 的操作仍确认 |

“帮我批准”按宿主的确定性规则分类，不额外请求模型替用户决定授权。缺失审批通道或用户拒绝时，手动确认操作不执行。

完全访问权限仍受当前工作区、可用工具、只读模式、版本与哈希检查约束；不会新增工具能力。它沿用已经开放的本地操作范围。项目 deny 规则不能被权限档位解除，明确 ask 规则通过工具包装、注册快照及子任务继承仍然保留。

所有档位都不改变数据发送前的既有模型服务授权流程，业务信息缺失时的 ask_user 也仍然有效。

## 执行层与任务快照

- TaskRecord 保存 PermissionMode；排队时就固定，后续修改偏好不改动旧队列任务。运行期间禁用权限切换，顶栏展示实际运行任务的固定档位。
- 子任务继承主任务档位；只读角色仍可进一步收紧权限。
- 原件文本修改即使自动批准，也由宿主创建绑定当前调用、提案、版本与参数哈希的授权，隔离 Worker 继续校验；不能靠模型参数声明“已批准”。
- 本地内核与远程适配器调用本地工具的入口采用同样的档位决策；远程服务自身的额外限制不由此解除。
- 自动批准敏感操作记录 PermissionAutoApproved 事件；手动批准/拒绝保持原有事件和对话内卡片。
- 旧配置/旧任务缺少档位字段时使用“帮我批准”，保持旧行为；无效字段回落到“请求批准”，无效任务枚举被拒绝。
- 新的权限菜单使用所属窗口的 ViewModel；审批卡显示具体成果文件名或原件差异，内部文档ID不作为主要审批文案。

## 验证

本轮重新构建、测试并打包。准确计数、二进制哈希及报告随包放在 verification。

新增验证包括三档成果审批、真实原件修改的调用绑定授权、拒绝后无文件、无效JSON不打断用户、项目 ask/deny 与只读优先级、配置与任务持久化、主子任务继承、文档草稿仅最终交付确认、本地适配工具入口、队列权限冻结、菜单选择与运行中锁定、上下文整理状态及800像素窗口渲染。

测试采用本机合成API和合成文件。本轮没有新增公网模型调用；1.0.4真实DeepSeek教案验证另见该版本记录，不并入本轮通过计数。

UI测试曾因产品App启动生命周期切换到共享配置，误写了权限字段。已核实其余字段与测试前自动备份完全一致，并按备份原字节恢复；随后将测试改为仅加载WPF资源的独立Application，后续回归使用工程内隔离存储，不再调用产品启动生命周期。

便携包不含用户聊天、任务数据库或测试存储。应用仍需要.NET Framework 4.8；Win7 SP1实机兼容性仍待验收。
