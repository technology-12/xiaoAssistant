# Claude Code / OpenCode 文档生成可靠性调研

调研日期：2026-11-05。范围：官方 GitHub 源码、已合并 PR、官方更新记录及文档；对照当前晓助手 1.0.3。此次只做调研与方案，不修改产品代码、不重打包，也未向真实模型发送用户文档。

## 结论

普通办公文档任务不应因为一次模型输出达到上限，就要求用户拆分文稿或重新开始。当前日志证明的是单次生成截断、工具参数格式错误，不能证明用户提供的文档数量超过系统合理承载能力。文档数量、输入上下文、单次输出 tokens、传输字节、工具参数长度、整份成果大小是不同指标。

1.0.3 的草稿分批是必要基础，但仍属于局部修补：模型需要主动使用草稿协议，截断恢复条件偏窄，整份文档还有固定限制。需要把自动编排、错误恢复、持久化成果和最终验收连接起来。

## 一、上游可核实的证据

### Claude Code：官方公开行为与证据边界

- [官方 CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md) 明确记录输出达到 token 限制后自动继续，并记录过大后台输出转为有限摘要和文件路径，以及文件读取返回部分视图的改进。这说明限制发生后应有恢复与按需读取机制，而不是立即结束整个用户任务。
- [官方输出额度环境变量参考](https://code.claude.com/docs/en/env-vars)：输出额度是可配置参数，应同时尊重模型支持的上限；不能把某一个默认数字当作所有模型的能力。
- [官方仓库问题 #45436](https://github.com/anthropics/claude-code/issues/45436) 也报告过 Write 参数被截断而写入失败。它是用户报告，关闭原因是重复问题，不能据此宣布最新版完全不会失败，也不能把报告中的 8K 当作全产品统一默认值。
- [官方 LICENSE](https://github.com/anthropics/claude-code/blob/main/LICENSE.md) 为保留所有权利、适用商业条款。官方公开仓库不能当作完整开源内核；此次没有使用泄露代码或非官方反编译材料。自动继续的具体内部算法、重试次数不能仅凭更新记录推断。

### OpenCode：可直接审阅的恢复实现

[已合并 PR #53876](https://github.com/anomalyco/opencode/pull/53876/files) 于 2026-10-13 合入 dev，直接处理输出达到限制的问题。审阅的变更涉及 runner 的 llm、step、事件发布与测试文件；PR 最后提交为 `9fcffed9e579210df170f276f56b01fefa80e118`。本报告以已合并变更为证据，不把“合入 dev”直接等同于某个发行包已经包含。

- step 将 `length` 建模为独立的 OutputLimit 结果。
- 编排器据此继续工作；没有等待用户再次发送“继续”。
- 读取最近的用户/助手消息判断连续截断，第三次连续截断才终止，即最多两次延续；正常结束或用户输入会打断连续计数。
- 参数不完整、JSON 非法和输出截断有不同反馈，未完成的调用明确标记未执行；恢复信息包含最多 2048 字符的参数片段及原长度。
- 恢复提示要求剩余工作缩小调用粒度，避免重复完成内容。

特别注意：这是带状态的继续，不是把半截 JSON 拼起来执行，也不等于无限重试。源码中的工具名修正功能同样不能宣传为任意 JSON 自动修复。

### 当前工程引用的是较早 OpenCode 版本

本地 `migration/upstream/opencode` 为 `v1.1.20`，提交 `09ff3b9bb925903b36aa35fec25394133a42cf6d`。不能因为工程参考过 OpenCode，就认为已具备后续全部可靠性改进。

- [v1.1.20 session/llm.ts](https://github.com/anomalyco/opencode/blob/v1.1.20/packages/opencode/src/session/llm.ts)：默认全局输出上限 32000，并结合模型额度计算；工具调用失败会通过 invalid 工具反馈，有限修正工具名。
- [v1.1.20 provider/transform.ts](https://github.com/anomalyco/opencode/blob/v1.1.20/packages/opencode/src/provider/transform.ts)：计算供应商及模型相关的输出额度，并处理部分供应商思考预算。不能简单把它改写为“永远允许 32K 正文”。
- [v1.1.20 tool/read.ts](https://github.com/anomalyco/opencode/blob/v1.1.20/packages/opencode/src/tool/read.ts)：支持 offset/limit，默认 2000 行，并限制返回字节。局部返回是分次读取的手段，不是拒绝处理整份文件。
- 本地同版本 `session/compaction.ts` 还根据模型上下文与输出预留判断压缩，并裁减较旧工具结果。这里只描述所审阅旧版本，不宣称当前各版本配置字段完全相同。

以上是通用智能体机制。此次证据不足以宣称 Claude Code 或 OpenCode 自带一个与晓助手相同的 DOCX 排版内核。

## 二、与当前实现的差异

| 环节 | 晓助手现状与定位 | 需要补齐 |
|---|---|---|

过去两条日志分别是 length 和约 8.9K 字符工具参数 JSON 非法。后者尚未进入 DOCX 写入器，不能归咎于 Office 安装、DOCX 容量或文档太多。现有记录也不足以承诺具体多少份、多少页必定成功。

## 三、建议改造设计（本项目方案，不声称上游原样实现）

### P0：模型调用恢复状态机

将输出结束、上下文溢出、网络中断、参数语法错误、schema 不符、执行失败作为不同状态。输出达到限制后：保存可信状态和 usage，保留完整已完成工具结果，对不完整调用返回未执行反馈，再开始下一次模型请求。显示过的文字允许保留后续接，不整段重放。

连续两次恢复仍无进展可以终止该恢复策略，但成功保存一个新章节或完成正常步骤应重置连续计数。任务总请求/费用/时间预算继续独立生效。预算耗尽时保存可恢复任务，不能宣称完成。

### P0：宿主管理文档生成

建议内部协议：begin_document → append_sections / patch_section → inspect_draft → finalize_document。宿主生成稳定文档 ID、章节 ID、revision 和幂等键，模型负责内容与结构。已有 write_word 作为兼容入口，逐步映射到内部流程。

不能在收到一个已经超限的完整工具参数后，才希望本地“自动切块”解决截断：必须在生成前规划小调用，出错后也要转入小调用。完整持久化的章节保留，未通过校验的半截调用不执行。

长正文优先存储本地章节文件，工具回复只返回 ID、已保存范围、下一步和摘要；后续按章节读取、替换。由本地 C# 排版器确定性合成 DOCX/PPTX，最终原子提交到 output。整个过程保持 Win7/.NET Framework 兼容，不要求加入 Bun、Node 或远程工具执行服务。

### P1：输入按需读取与上下文管理

先列文件、提取标题/段落索引，再按任务定位阅读。需要全文审阅时必须遍历全部范围并跟踪覆盖，不能以检索代替完整审阅。压缩历史时保留原始文件引用、用户约束、成果清单、已完成章节、未完成项及草稿版本；旧正文可重新按 ID 读取。

### P1：额度与资源限制分层

分别维护模型上下文、单次输出、响应字节、单调用参数、草稿磁盘、最终文档资源与任务总预算。不默认假设任何 OpenAI 兼容端点都支持同一个 token 上限。不盲目请求模型最大输出，也不因增加 token 配置而取消自动分批。

优先解除20批/200块这类会意外限制正常长文的固定产品限制，换为可配置资源预算、分页读写和明确的进度信息；实施前评估当前每批重新合成整份草稿造成的重复开销，避免放大上限后出现新卡顿。

### P1：完整成果验收

任务开始记录预期文件与内容要求。最终检查全部目标文件存在、OOXML 可解析、文本和章节覆盖、无重复批次、无明显截断、文件能通过独立读取器回读；需要版式验收的样稿另做实际 Word/WPS 打开或渲染检查。只有所有必需成果通过才报告完整完成。

## 四、验收计划

1. 用脱敏或合成语料建立与用户实际数量、字数、表格复杂度相当的基准；尚未确认这些统计前，不编造承载结论。
2. 增加1/5/10份中文文档、单份1万/3万/8万字符、含长表格、原稿修改和多成果任务。它们是建议测试档位，不是目前通过的承诺。
3. 使用真实目标供应商 API，测试正常调用、较小输出额度、连续截断、非法参数后改用小调用；记录每次实际额度、finish_reason、usage、恢复原因、有效新增内容与最后结果。
4. 验证显示文字后截断可继续；某份失败不重生成已成功文件；重复调用不重复内容；中断后恢复草稿；全部预期成果均回读通过。
5. UI 持续显示处理中/已完成数量，不能卡死或提前宣告完成。发布门槛包含真实 API 结果和换机验证，不能仅凭模拟测试数量重新打包宣称问题彻底解决。

本次交付到此为调研结论与可实施方案。源码、运行配置、发布包均未在本次调研中修改。
